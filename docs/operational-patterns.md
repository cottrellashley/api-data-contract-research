# Operational patterns for independent API, client, and data evolution

Research date: **2026-10-20**. This chapter extends the API and data-contract research with operation-level consistency, release verification, event contracts, discovery, caching, and retirement. Vendor facts and standards are explicitly attributed. Unattributed architectures, examples, matrices, and policies are **proposed designs for the spike**, not claims about a vendor's private implementation. Examples are illustrative, not executable production configuration.

## 1. The compatibility unit is often an operation, not a request

A gateway receives individual HTTP requests, but a user performs operations: create a deployment and wait for readiness; query a dataset and collect every page; start an export and download it later; retry a timed-out update; consume a notification generated by an earlier write. A version header on the initial request does not by itself preserve the operation's meaning.

For this platform, define an operation context with independently meaningful identifiers:

| Context | Purpose | Where it must survive |
|---|---|---|
| API contract | Request, envelope, error, and workflow behavior | Every related HTTP request and stored job |
| Data contract | Public fields, units, grain, and meaning | Results, jobs, export metadata, relevant events |
| Published snapshot | A particular validated dataset state | Page cursors, resumable exports, reproducibility records |
| Adapter revision | How source data was interpreted | Lineage and replay records; usually internal |
| Authorization context | Who may perform the operation or read its result | Every authorization check; never only the first request |
| Idempotency identity | Which retries belong to one intended mutation | Mutation execution and response reconstruction |

Do not expose every internal revision as a required client parameter. Record internal identities for debugging and replay; expose only the controls that customers need to make a meaningful choice.

### Failure scenario: an export changes while it runs

1. A Python client submits an export using API v1 and orders data contract 2.
2. The worker reads the current contract alias when it starts, rather than the selected contract stored with the job.
3. A data owner promotes contract 3 before the worker starts.
4. The export succeeds technically but contains renamed columns and different amount semantics.

**Proposed remedy:** resolve mutable aliases when accepting a job, store the immutable selection in the job, and verify workers can execute that selection. If a mutable "latest data" mode is intentional, document when it resolves. Specify separately whether data is captured at submission, execution start, or query transaction start. A contract ID alone does not identify a data snapshot.

## 2. Build a compatibility evidence matrix

There are at least four different proofs. None subsumes the others.

| Evidence | What it can establish | What it cannot establish by itself |
|---|---|---|
| Specification compatibility comparison | A candidate schema satisfies chosen structural evolution rules | Actual server conformance, semantic equivalence, or client behavior |
| Provider/consumer contract verification | Recorded requests and expectations remain satisfied | Unrecorded integrations, arbitrary production data, complete workflows |
| Historical client artifact execution | Selected real clients still work on tested scenarios | Every client release, customer environment, or input distribution |
| Data replay and reconciliation | Candidate interpretation behaves acceptably on retained and synthetic data | Unseen future source behavior or unobservable semantic changes |

### Consumer-driven contract testing: useful, with a bounded claim

**Documented tool behavior:** Pact records consumer expectations and verifies them against a provider. Its broker associates results with application versions and uses this matrix for deployment checks. Provider verification is designed for controlled local/CI execution; dependencies can be stubbed below the request parsing and validation boundary. [Pact provider verification](https://docs.pact.io/provider), [Pact deployment matrix](https://docs.pact.io/pact_broker/can_i_deploy)

**Design conclusion:** use consumer-driven contracts for first-party CLI/SDK integrations and participating internal consumers. Retain provider-owned public contract tests for endpoints available to arbitrary curl users. An empty broker list for a field is not proof that no customer uses it. A passing stubbed provider test is not evidence that an uncontrolled source continues delivering valid records.

In particular, avoid the argument "all pacts passed, so we can remove this public field." The completeness of the consumer inventory is an architectural assumption. For public client packages downloaded into unknown installations, that assumption usually does not hold.

### Preserve the actual artifacts users installed

For Go CLI releases, retain signed/checksummed release binaries and platform metadata. For Python, retain released wheels, their hashes, supported interpreter ranges, and representative dependency lock sets. Rebuilding the old Git tag with today's generator and dependencies may produce a different program from the one users installed.

Two Python scenarios answer different questions:

1. A historically pinned environment calling the new server.
2. A fresh installation of the old SDK under its published dependency constraints.

The first models long-lived automation. The second finds breakages caused by dependency resolution, interpreter support, or packaging metadata. Do not claim network API compatibility covers installation compatibility.

Keep artifacts in isolated test environments with test credentials and restricted access. Running old binaries against production data is unnecessary for these checks. Where an old runtime is no longer acceptable to execute, record that limit explicitly rather than presenting simulated decoding as equivalent evidence.

### Proposed release matrix

| Consumer | Provider/data configuration | Required evidence |
|---|---|---|
| Oldest supported CLI | Candidate provider, existing source shape | Existing commands, flags, exit codes, and structured output |
| Latest stable CLI | Candidate provider, candidate source shape | Existing and new workflows, explicit feature failures |
| Representative older Python wheels | Candidate provider, generated edge cases | Imports, serialization, decoding, pagination, error handling |
| Raw HTTP client | Every supported public API projection | Contract works without official SDK middleware |
| Candidate CLI/SDK | Oldest supported server | Unsupported features fail predictably before mutation when possible |
| Existing consumers | New records written through a newer contract | Reads and updates preserve fields older models do not understand |
| Event handler versions | Historical and newly generated events | Duplicate handling, decoding, ordering assumptions |
| Export reader | Result generated before and after publication swap | Schema and snapshot remain consistent within each operation |

Test the oldest supported and newest releases as boundaries, plus releases with known serialization, generator, or protocol transitions. If that is sampling rather than exhaustive testing, say so. A single umbrella "supported" badge should not hide materially different evidence.

### Mutation-based fixture suite

Start with a representative source record and independently introduce: additional fields, unknown enum values, null, missing field, empty string, maximum integer, fractional amount, timezone offset, duplicate key identity, late arrival, unexpected nesting, and new status transitions. Also include records that remain structurally valid but violate units, grain, or totals.

Assertions should measure public behavior: no silent truncation; no loss of unrelated fields during update; correct error category; old serializer still accepts the result; published aggregate does not silently omit invalid records. Tests that merely serialize a model generated from the same specification are insufficient evidence against real-world drift.

## 3. Separate control-plane and data-plane contracts

**Documented Azure pattern:** management operations use the control plane; operations using a resource's capabilities use its data plane. Azure notes that data-plane access can continue during control-plane unavailability, and that management governance does not necessarily govern data operations. [Azure control and data planes](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/control-plane-and-data-plane)

**Proposed application to this spike:** classify operations by their promises before choosing services or endpoints.

| Control-plane concerns | Data-plane concerns |
|---|---|
| Register source, credentials, owner, and contract | Read, ingest, transform, and query records |
| Promote a contract or adapter | Serve a selected published snapshot |
| Configure retention and permissions | Enforce access and masking on returned data |
| Inspect deployment capabilities | Execute workload under those capabilities |

This separation can be logical initially. It does not require two clusters or gateways. It becomes operationally valuable when existing reads must continue while configuration changes are unavailable.

Avoid loading mutable contract definitions from the control plane on every data request without a continuity strategy. Prefer validated, immutable execution bundles distributed to serving processes, with a recorded active generation. If configuration distribution is temporarily unavailable, continue only under the documented validity policy for an already accepted bundle.

Authentication and authorization still apply independently to data operations. Permission to configure a data source does not automatically grant permission to read all source data. Conversely, freezing a management resource does not necessarily prevent a SQL client from modifying records unless the data path enforces the intended restriction.

## 4. Capabilities and version negotiation

**Recommendation:** a capability endpoint is useful for self-hosted installations, staged cloud rollouts, tenant entitlements, and source-specific features. It supplements an explicit supported API matrix. It is not proof that a subsequent mutation will succeed.

Illustrative response:

```json
{
  "discovery_version": "1",
  "api_versions": ["v1", "v2"],
  "configuration_generation": "rollout-42",
  "capabilities": {
    "orders.export": {"available": true, "contract_versions": ["2"]},
    "orders.bulk_update": {"available": false}
  }
}
```

Define capabilities as behavior, not build-number comparisons. A client can know how to use `orders.export` without understanding every future server version. Unknown capabilities are ignored; missing capabilities mean unknown/unavailable under an explicit protocol rule, rather than an invitation to guess.

Discovery may depend on tenant, region, authorization, edition, feature flag, and selected source. Cache it accordingly, and make any freshness assumptions explicit. Sensitive feature or resource existence may itself require authorization.

### The discovery race

A CLI reads capabilities from replica A, which has a new feature. Its write is routed to replica B, which has not upgraded. The feature was advertised but the write fails. Worse, the client automatically falls back to an older mutation with different semantics.

**Proposed choices:** advertise only the intersection guaranteed by all eligible replicas, route a capability generation to a compatible pool, or return an explicit unsupported-generation error. Enforce capabilities again at execution. Do not treat discovery as a lock or authorization grant. If execution fails, refresh discovery when appropriate; do not blindly downgrade and retry a write.

### Version selection policy

For official clients, default to a tested API contract. If supporting negotiation, select only from versions that the installed client actually implements. "Server supports v4" does not teach a v1-era SDK how to serialize v4 requests.

Return the selected contract in response metadata and persist it in operation records. For public APIs, an explicit unsupported-version error is easier to diagnose than silent substitution. Offer a deliberate compatibility mode only if its behavior and downgrade losses are defined.

## 5. Idempotency, retries, and transformation boundaries

**Documented vendor example:** Stripe currently distinguishes API v1 and v2 idempotency. V1 stores the first response after execution begins, including server errors; parameter differences are rejected for an existing key. Its documentation describes different retry completion behavior for v2. Therefore "Stripe caches the first response" is not a universal statement about all Stripe APIs. [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)

**Proposed rule:** an idempotency key identifies an intended operation within a defined scope. Specify that scope, retention, conflict behavior, concurrent-request behavior, and treatment of partial upstream execution.

For this platform, an idempotency record should bind:

- Tenant/account and operation identity.
- Original selected API and data contract.
- Canonical request fingerprint under that contract's semantics.
- Execution state and any downstream idempotency references.
- Original response representation or enough immutable information to reproduce it.
- Retention/expiry policy.

The lookup must detect a repeated key before treating a changed API version as an entirely unrelated new operation. A design that simply includes version in the key namespace can accidentally execute a downgraded retry twice. Reject conflicting reuse or deliberately resume the original operation; choose and document one policy.

### Failure scenario: retries cross an adapter promotion

1. Request A under contract 1 maps `amount: 100` into 100 cents.
2. The upstream commits, but the gateway loses the response.
3. A configuration change modifies an adapter's amount interpretation.
4. The retry is transformed again and sent as a different upstream request.

**Proposed remedy:** retain the original interpreted operation and execution identity. Resume that operation. Do not interpret a retry against a mutable mapping alias. If the upstream cannot provide deduplication or reconciliation, the gateway cannot manufacture a general exactly-once guarantee. Expose an indeterminate state and provide a way to inspect/reconcile it.

Retry policies also need deadlines, bounded attempts, backoff, and cancellation semantics. A canceled local wait does not imply the remote operation was canceled. Keep that distinction visible in CLI messages and SDK exceptions.

## 6. Pagination, cursors, and long-running jobs

**Documented guidance:** Google AIP-158 recommends pagination from the outset, opaque page tokens, and consistent request arguments across pages, with page size as an allowed exception. It warns that introducing pagination later is incompatible. A page can be empty while still having a continuation token. [Google AIP-158](https://google.aip.dev/158)

**Proposed cursor context:** bind the selected API contract, data contract, query/filter/sort interpretation, dataset snapshot or consistency mode, tenant scope, position, and expiry. This can be an authenticated opaque token or a server-side lookup. Encoding JSON as base64 alone does not provide integrity or confidentiality.

Authorization must be reevaluated on subsequent requests. A cursor is not a permanent permission grant. If access has been revoked, stop access even when a snapshot remains available. Signed cursor integrity does not settle that policy.

Specify what happens when a snapshot expires: explicit expiration and restart instructions, rather than silently continuing against fresh data. If the product offers live pagination rather than a consistent snapshot, document possible duplicates/omissions under concurrent change and provide stable ordering requirements.

For SDKs, preserve version selection and request options across internally generated page calls. Test an empty page with a nonempty continuation token. Stop because the continuation contract says to stop, not because a page happened to have zero rows.

For long-running operations, separate the operation-status contract from the final-result contract. A job can report `succeeded` while its downloadable artifact requires an older data schema. Preserve both identifiers. Define retention for status records and result artifacts independently, and provide explicit expired-result behavior.

## 7. Cache correctness is part of contract correctness

**HTTP standard:** RFC 9111 defines response selection using `Vary`, authenticated-response restrictions, cache directives, and freshness. These mechanisms concern HTTP caches; they do not automatically configure an application's Redis keys or internal object cache. [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html)

**Proposed effective cache identity:** include every input that changes the permitted representation. Depending on the endpoint, these may include tenant, authorization partition or policy generation, API version, data contract, snapshot, projection, filter, sort, locale, timezone, and relevant feature configuration. A data-contract version header must affect cache selection when it affects the response.

Do not include access tokens in logs or metric labels. For internal caches, derive an appropriate access partition rather than exposing credentials as readable cache-key material. If authorization partitions cannot be modeled safely, disable shared response caching for that operation.

### Failure scenarios

| Missing distinction | Consequence |
|---|---|
| API or data contract | Old SDK receives a new representation from cache |
| Tenant/access partition | One customer receives another customer's records |
| Snapshot | An export page is assembled from a different publication |
| Redaction-policy revision | Data remains visible after a masking rule changes |
| Query semantics | A correct-looking result answers an earlier interpretation |

Authorization on cache hits is still required under the chosen security model. A last-known-good data result must not bypass a newly revoked permission. Separate stale-data allowance from stale-permission allowance; they are different decisions.

ETags and conditional reads should identify the representation to which they apply. A single database row revision is not automatically a valid strong validator for two differently serialized public representations.

## 8. Streaming, webhooks, and event contracts

**Specification fact:** CloudEvents distinguishes its envelope `specversion` from payload schema information in `dataschema`; event identity uses `source` and `id`. A shared envelope does not define the business payload. This chapter references the released 1.0.2 specification rather than the changing `main` draft. [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)

**Vendor example:** Stripe documents duplicate delivery and lack of guaranteed event ordering. Its snapshot destination configuration selects an API version; request-version overrides should not be assumed to control every event representation. Existing event objects retain their original representation. These facts require independent webhook upgrade planning. [Stripe webhook guidance](https://docs.stripe.com/webhooks)

**Proposed event contract:** record event type, event/payload contract, identity, source, occurrence time, production time, correlation/causation, and relevant dataset or object revision. Decide whether the event carries a historical snapshot or merely announces that consumers should fetch current state.

| Event model | Advantage | Compatibility cost |
|---|---|---|
| Snapshot payload | Consumer can interpret the occurrence without a later fetch | Payload decoder must survive delayed delivery and replay |
| Notification with resource reference | Smaller event contract; consumer fetches using its chosen read API | Read may observe newer state, deleted resource, or changed permissions |
| Immutable change record | Supports audit and deterministic reconstruction if sufficient | Requires explicit correction, ordering, and retention semantics |

Do not present a reference-only notification as equivalent to an event-time snapshot. Fetching an order after three subsequent updates does not reconstruct its earlier state.

### Proposed delivery and replay design

Persist accepted event identity before acknowledging durable acceptance. Make processing idempotent with respect to the effect being applied, not merely the arrival of a message. A crash between performing an effect and recording completion is a specific scenario to test.

Use a transactional outbox or another explicitly justified atomicity strategy when a database update and event publication must agree. An outbox prevents one class of dual-write loss; it does not by itself establish exactly-once processing at every subscriber.

For replay, preserve original payload and schema identity under a retention policy. Apply explicit upcasters/adapters when reading old events. Decide whether a correction produces a new corrective event, a new projection, or a rebuilt snapshot. Avoid silently rewriting historical event bytes in place while keeping the same identity.

Version stored offsets and checkpoint formats if parser or partitioning changes affect their interpretation. A new consumer binary that can decode old payloads may still fail to resume an old checkpoint.

## 9. Rolling upgrades and a support-skew policy

**Documented precedent:** Kubernetes publishes explicit version-skew limits. Its `kubectl` policy supports one minor version older or newer than the API server; mixed server versions narrow the allowable range. This is an example of a bounded compatibility promise, not a policy every SaaS should copy. [Kubernetes version-skew policy](https://kubernetes.io/releases/version-skew-policy/)

**Proposed release sequence:** expand storage and accepted inputs; deploy readers that tolerate the expanded representation; deploy writers and adapters; enable new behavior after the reachable serving fleet can honor it; release client features; retire old behavior only after its promised window and evidence requirements are satisfied.

During the overlap, reason about all reachable combinations:

```text
old client → old replica → old/new record
old client → new replica → old/new record
new client → old replica → old/new record
new client → new replica → old/new record
```

For rolling adapter updates, add old/new mappings and old/new source shapes to that matrix. A load balancer makes mixed replicas ordinary, not exceptional. A rollback must still read records written during the new release. If the older build cannot do so, rollback may require a forward fix, writer disablement, or restoration strategy rather than simply redeploying an old image.

Do not infer that API v1 support means every ancient CLI remains supported indefinitely. Publish separate lifecycles for public contracts, SDK releases, supported runtimes, CLI releases, and data snapshots. An old release can remain interoperable after maintenance ends; those are distinct claims.

## 10. Observability without uncontrolled cardinality

**Documented operational constraint:** Prometheus warns that every unique label combination creates a time series and advises against unbounded dimensions such as user IDs. [Prometheus metric naming](https://prometheus.io/docs/practices/naming/)

**Proposed telemetry split:**

| Channel | Appropriate context |
|---|---|
| Aggregate metrics | Route template, API major, contract family, bounded compatibility class, outcome category |
| Structured logs/traces | Request ID, job ID, exact SDK version, schema ID, adapter revision, snapshot ID, carefully controlled tenant reference |
| Adoption analysis store | Per-customer contract/client usage with suitable access and retention |
| Data-quality reporting | Completeness denominator, invalid records, freshness, quarantine, reconciliation deviation |

Do not label every metric by arbitrary schema hash, raw URL, tenant ID, and full user agent. The combined cardinality is multiplicative. Classify unknown/unparseable client versions into a bounded category and retain exact values where useful in logs.

Track both HTTP success and data usefulness. A server returning 200 with a complete JSON body can still violate freshness, completeness, or semantic expectations. Suggested separate indicators are valid-published-batch ratio, age of last valid publication, rejected-source-record ratio, and compatibility error rate for supported clients.

Define the denominator carefully. "Invalid record rate dropped" may mean the upstream stopped sending an entire category of records. Volume and reconciliation checks complement per-record validation.

For retirement analysis, lack of recent usage is evidence with a time window, not proof of absence. Monthly reports, disaster-recovery jobs, and dormant installations can be legitimate supported consumers. Use contract commitments and customer communication alongside observed traffic.

## 11. Retirement signaling and enforcement

**HTTP lifecycle facts:** `Deprecation` signals lifecycle status without changing resource behavior and can link to explanatory documentation. `Sunset` communicates anticipated unavailability; RFC 8594 is Informational, whereas RFC 9745 is Standards Track. These headers do not force existing clients to display warnings or migrate. [RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html), [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594.html)

**Proposed lifecycle:** candidate → supported → deprecated → retired. Keep maintenance/support status for client packages as separate metadata. Each transition should identify owner, affected contract, replacement, published dates, notification evidence, exceptions, and enforcement plan.

SDKs can expose deprecation metadata and emit configurable warnings; CLIs can display notices on stderr so JSON stdout remains parseable. Avoid turning every successful SDK request into noisy application output. Do not depend solely on a warning introduced in a newer client to notify users still on old clients.

At retirement, return a stable machine-readable error identifying the retired contract and migration information. Do not silently route an old request to a new incompatible contract. Define how in-flight jobs, existing cursors, downloaded exports, and stored events are handled at the deadline. A graceful drain policy for accepted operations may differ from the cutoff for starting new work.

## 12. Recommended first spike experiments

These experiments exercise the architectural decisions rather than committing the system to particular vendors.

1. **Historical client:** run one real old Go CLI and one old Python wheel against a provider that adds an enum, null, and response field. Record actual decoder behavior.
2. **Data-only change:** hold all binaries constant, alter source shape and mapping configuration, and demonstrate detection plus controlled publication.
3. **Mixed replicas:** route discovery to a new replica and execution to an old replica. Verify explicit capability handling.
4. **Ambiguous write:** commit upstream, lose the response, promote an adapter, and retry. Confirm one intended operation or a documented indeterminate outcome.
5. **Cursor continuity:** paginate while promoting a new data contract and snapshot. Verify continuation remains bound or fails explicitly on expiry.
6. **Cache partition:** issue equivalent URLs across two tenants, two contract versions, and a permission change. Verify no cross-context reuse.
7. **Event replay:** process old/new events out of order and with duplicates, then restart between side effect and checkpoint.
8. **Rollback readability:** create data with the new writer, roll back the reader, and demonstrate the documented supported behavior.
9. **Silent semantic drift:** keep types fixed while changing units or record grain. Verify reconciliation catches what schema validation misses.
10. **Retirement:** test an old client that ignores headers and one that displays them; verify terminal errors and in-flight operation policy independently.

Success means the team can state which boundaries are guaranteed, how each guarantee is tested, and what happens when upstream information makes a guarantee impossible. It does not mean every source mutation can be transformed automatically.
